# M5 handoff: artifacts and command-line helpers

Status: the M5 checkpoint passes. S6's helper and artifact prerequisites have
evidence for the selected profiles on macOS arm64, Linux x86-64 and Linux
arm64. The handoff run is recorded in
[handoff-evidence/manifest.json](handoff-evidence/manifest.json) and
reproduced by [run-evidence.sh](handoff-evidence/run-evidence.sh), whose Linux
part is [linux-evidence.sh](handoff-evidence/linux-evidence.sh). Passing M5
does not claim S6: the native IronJarMain, IronDoc and class-output commands
are S6's ports, and S6 compares them with the Java tools.

## Selected profiles (D275)

| Profile | Reader | Writer |
| --- | --- | --- |
| `.ironclass` | `ZipStream`: local headers in order, Java's `ZipInputStream` model, with Ironwood inflate | STORED in Java's STORED spelling, written directly (`IronClass.write` keeps its direct write) |
| `.ironjar` | `ZipArchive`: the central directory, Java's `ZipFile` model, with Ironwood inflate for DEFLATED entries and nested DEFLATED class payloads | STORED in Java's spelling, staged in the destination's parent and published with `moveReplacing` |
| Bridge JAR | (no native reader needed) | STORED in Java's spelling; M5.2 opens it with `jar`, `java -jar` and a class loader; BridgeJarArchive's port and its `moveAtomicReplacing` publication are M6/S7 |

Every reader accepts STORED and DEFLATED entries; no profile has a
STORED-only reader. Four native policies are recorded beside Java's exact
profile messages: CRC and sizes are verified for every entry read, a malformed
entry name is an artifact error, the array range is an explicit size limit,
and container defects get native `invalid ZIP data in <archive>: ...`
messages. A native `.ironjar` equals Java's for equal payloads; native
`.ironclass` and Bridge JAR bytes, and any identity over them, differ from the
Java bootstrap's DEFLATED output (3.0 times larger class artifacts).

| Host | Result |

- Readers and writers hold whole archives in memory; the measured peaks run
  from 1.9 MB for one small class artifact to 404.9 MB for an archive with a
  128 MiB license ([ARTIFACTS.md](ARTIFACTS.md#peak-memory)).
- Inflate is one-shot over an in-memory range; a streaming consumer would need
  incremental input. There is no compressor.
- The recorded differences from the Java baseline are verified CRC and sizes
  in IronJar entries, a malformed class entry name as an artifact error,
  native container messages, the first missing indexed entry named in index
  order, a traversal failure inside an archive input or library root reported
  as an IOException, and STORED class artifact bytes
  ([ARTIFACTS.md](ARTIFACTS.md#behavior-against-the-java-baseline)).
- Publication has no fsync or durability policy, as decided for M5; class
  artifacts are written directly.
- Representation limits the port code works within, none needing runtime
  overhead: a `StringBuilder` made from a String cannot be freed (the port
  builds with `new StringBuilder()` and appends); a caught exception and its
  message cannot be freed, so each ignored discovery root and each caught
  entity diagnostic keeps two allocations; `SimpleFileVisitor` lacks
  `throws IOException`, so `FileCollector` implements `FileVisitor`; creation
  arrays lend storage only to `runToFile`, so archive inputs are `TextList`
  owners.
- `DocText.regionMatchesIgnoreCase` compares UTF-16 units, which equals Java
  for the ASCII literals its callers pass; the scans implement their call
  sites' expressions, not a regular-expression engine.

## Handoff run

One run on a fresh `git archive` of 4c1c66ce: the strict `scripts/build.sh`,
`javac --release 21 -Xlint:all -Werror` over every compiler test source, 42
macOS tests (the 25 M5 tests in
[m5-tests.txt](handoff-evidence/m5-tests.txt) and 17 consumers: the three
Ironwood archive tests, the library round trip, IronDocs, SHA-256, both
borrow-dispatch tests, the three U5 traversals, M4.1's allocation-failure
sweep, M4.2's publication moves, tree deletion, installation discovery, the
backend helpers and the port generics audit), the three M5 classifications
byte for byte with the five earlier tables unchanged, one compilation of all
187 port sources with the five pilot adapters under `--unfreed=warn` (no
diagnostics), `git diff --check` over ea19508c..4c1c66ce, the license audit,
and on estonia and miami the 25 M5 tests with the U5 traversals, M4.1's sweep
and tree deletion. All 26 statuses passed. The macOS part started once the
one-minute load fell below 3, with the Linux arm64 guest running beside it.
Unsafe programs were compile-only; no full suite or hosted build ran.

The first checkpoint run found two defects in earlier M5 commits, both fixed
before this run. The four frozen Java-written `.ironclass` fixtures matched
the `*.ironclass` ignore rule and had never been committed, so a clean archive
failed the eight fixture-based tests on estonia; 5ee3e8d3 tracks them through
an ignore exception. `git diff --check` over the range flagged two of Java's
exact diagnostics in the frozen verdict transcript that end in whitespace;
4c1c66ce exempts that byte-exact file. Per-commit checks had missed both: the
working tree held the fixtures, and `git diff --check` without `--cached`
skips newly added files. That run, on 5ee3e8d3, passed every test on the
three hosts.

The range also contains f50038c0, a separate task's fix that keeps ownership
refinement after import-only errors. It is not M5 work; the M5 tests ran with
it in place.
