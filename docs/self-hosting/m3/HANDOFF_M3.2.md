# M3.2 handoff: passing before the S3 consumers

Status: M3.2 passes. Its helpers are ready for their S3 consumers, ByteView
first: bounded numeric folding, StringPool/UTF-16 and name helpers, and exact
SHA-256 with ByteView declaration authority. The handoff run is recorded in
[m3.2-evidence/manifest.json](m3.2-evidence/manifest.json) and reproduced by
[run-evidence.sh](m3.2-evidence/run-evidence.sh). S3 itself has not started.

## Capacity evidence

The pinned profile was `-Xms256m -Xmx4096m -Xss8m -XX:+UseG1GC` with
`JAVA_TOOL_OPTIONS`, `JDK_JAVA_OPTIONS` and `_JAVA_OPTIONS` cleared, which
`-XX:+PrintCommandLineFlags` confirms in each log. The input was every one of
the 160 sources under `compiler/src/main/ironwood` plus the five M2 pilot
adapters, in one invocation, each link at `-O3` with `--unfreed=warn`. Runs
were serial and each began only after the one-minute load fell below 3 (start
loads 2.55-2.99). Heap is the largest G1 post-pause occupancy sampled in the
GC log; RSS is the `time -l` maximum resident set.

| Step | Exit | Wall (s) | Max RSS (MB) | Sampled heap (MB) |
| --- | --- | --- | --- | --- |
| J0 compile, run 1 | 1 (expected) | 11.343 | 950 | 532 |
| J0 compile, run 2 | 1 (expected) | 11.459 | 1,069 | 592 |
| Handoff compile, run 1 | 0 | 13.600 | 992 | 555 |
| Handoff compile, run 2 | 0 | 13.635 | 1,104 | 612 |
| Frontend pilot link, run 1 | 0 | 15.527 | 1,020 | 605 |
| Frontend pilot link, run 2 | 0 | 15.730 | 1,159 | 692 |
| Kernel pilot link, run 1 | 0 | 8.982 | 1,088 | 598 |
| Kernel pilot link, run 2 | 0 | 8.498 | 1,027 | 480 |

No step overflowed its stack and the largest sampled heap is under a fifth of
the 4 GiB limit. The handoff compile reported no diagnostics.

**Seed finding.** J0 (0.6.1-beta, seed 6bde84df, jar sha256 `2a8b10ab...`)
cannot compile the accumulated port: its 182 errors
([j0-errors.txt](m3.2-evidence/logs/j0-errors.txt.gz)) are missing M1 library
members (the `copy` methods of `ArrayList` and the hash maps and sets, D248)
with their follow-on type errors, and frees whose proofs need the M1 analysis
(D248-D254), such as caller-frame builders across exceptional paths and
destructor frees of owned fields. The helpers are correct; J0 predates the
library and proofs the port relies on. This is the case the plan's step 3
anticipates: S3's capacity qualification must record a newer seed revision and
its input manifest (here the handoff build of 776a9efc, jar sha256 in
[build-identity.txt](m3.2-evidence/logs/build-identity.txt.gz)) while the
original J0 baseline stays the reference for Java behavior.

## What the S3 consumers must still do

- ByteViewIntrinsic and BridgeGeneration switch to `Sha256` and keep the
  source/class/archive authority cases of the SEMANTIC fixture as their exit.
- FunctionAnalyzer and StaticConstantEvaluator adopt `IntegerLiterals` and
  `IntegralConstants` behind the explicit constant representation (class B
  rows), and check the native floating-to-integral casts against Java there.
- StringPool adopts `Texts.utf8Length` and `codePoint`; each consumer writes
  its own fixture against the Java baseline.
- S3 qualifies capacity on its recorded seed, rerunning this profile as the
  analyzer port grows.

## Retained limits

These are conservative rejections, not safety gaps:

- A digest's first construction triggers one process-lived class-init
  allocation (its round constants).
- Caught exceptions stay allocated, as M1 records.
- The M3.1 retained limits still apply.

## Handoff run

One run on a fresh `git archive` of 776a9efc: the strict `scripts/build.sh`,
`javac --release 21 -Xlint:all -Werror` over every compiler test source, and
17 focused tests: the seven M3.2 tests, the reference-bound audit over every
port source and the nine M2 pilot tests. The classification, the capacity
runs and the diff and license audits also ran. Unsafe programs were
compile-only; no full suite or hosted build ran.
